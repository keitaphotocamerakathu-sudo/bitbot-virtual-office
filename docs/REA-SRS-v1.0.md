# REA AI TRADING BOT — BITKUB
**Software Requirements Specification (SRS) v1.0**

**เป้าหมาย:** ระบบ AI Trading Bot ซื้อขายคริปโตอัตโนมัติบน Bitkub ตลอด 24 ชั่วโมง พร้อมระบบเลือกเหรียญ Multi-Agent, Risk Manager, Dashboard และประวัติการตัดสินใจที่ตรวจสอบย้อนหลังได้

**สถานะเริ่มต้น:** `PAPER_ONLY` — ไม่มีสิทธิ์ส่งคำสั่งซื้อขายจริง

## 1. ขอบเขตระบบ

- ใช้ทุนอ้างอิงเริ่มต้น 10,000 บาท
- ซื้อขายเฉพาะ Spot Trading คู่เงินบาท (THB)
- ไม่ใช้ Futures, Margin หรือ Leverage
- AI เลือกเหรียญที่เหมาะสมได้อัตโนมัติ โดยไม่บังคับให้เจ้าของเลือกเหรียญล่วงหน้า
- เปิดสถานะพร้อมกันสูงสุด 2 สถานะ
- ระบบวิเคราะห์และจัดการความเสี่ยงทำงานต่อเนื่อง 24/7 บน Backend
- เว็บ Dashboard ใช้ดูข้อมูลและควบคุม ไม่เป็นตัวประมวลผลหลัก
- รองรับ Paper Trading และ Live Trading แต่ต้องผ่านการตรวจรับก่อนเปิดใช้งาน Live
- ใช้แนวคิด Hummingbot/Condor Multi-Agent โดยไม่สมมติว่ามี Bitkub Connector สำเร็จรูปแล้ว

## 2. AI Multi-Agent Architecture

แบ่งงานออกเป็น 7 ส่วนหลัก

| Agent | หน้าที่ |
|---|---|
| Market Scanner | อ่านราคา Volume Spread และ Order Book ของเหรียญบน Bitkub |
| Technical Analyst | วิเคราะห์ EMA, RSI, MACD, ATR แนวรับแนวต้าน |
| News Analyst | ดึงข่าว ตรวจวันเผยแพร่ แหล่งข่าว และประเมิน Sentiment |
| Strategy Agent | จัดอันดับเหรียญและเลือกกลยุทธ์ที่เหมาะกับภาวะตลาด |
| Risk Manager | ตรวจทุน ความเสี่ยง จำนวนสถานะ และเงื่อนไขหยุดซื้อ |
| Execution Engine | ควบคุมการสร้าง ติดตาม ยกเลิก และกระทบยอดคำสั่ง |
| Supervisor & Auditor | ตรวจสุขภาพระบบ บันทึกเหตุการณ์ และตรวจความผิดปกติ |

**ข้อบังคับ:** Risk Manager ต้องใช้กฎที่ตรวจสอบได้ในโค้ด ไม่อนุญาตให้ LLM ปรับวงเงินความเสี่ยงหรือข้ามระบบอนุมัติการส่งคำสั่งด้วยตัวเอง

## 3. ระบบเลือกเหรียญอัตโนมัติ

**ขั้นที่ 1 — Market Discovery**

อ่านรายชื่อเหรียญที่เปิดซื้อขายบน Bitkub แล้วกรองเฉพาะคู่ THB ที่ API รองรับและสามารถส่งคำสั่งได้จริง

ตัดเหรียญที่สภาพคล่องไม่เพียงพอ ส่วนต่าง Bid/Ask สูงผิดปกติ ข้อมูลราคาขาดหาย ตลาดถูกระงับ หรือมีความผันผวนเกินเกณฑ์ออกก่อน

**ขั้นที่ 2 — Market Scoring**

คะแนนรวมเต็ม 100 คะแนน โดยเสนอค่าน้ำหนักเริ่มต้นดังนี้

| ปัจจัย | คะแนน |
|---|---:|
| แนวโน้มราคา | 25 |
| Momentum | 20 |
| Volume และสภาพคล่อง | 20 |
| ความผันผวนและ Spread | 15 |
| ความสอดคล้องกับกลยุทธ์ | 15 |
| ข่าวสารที่ตรวจสอบได้ | 5 |

คะแนนเหล่านี้เป็นสมมติฐานเริ่มต้น ต้องปรับจากข้อมูลย้อนหลังจริง ไม่ใช่สูตรที่พิสูจน์แล้วว่าสร้างกำไร

**ขั้นที่ 3 — Auto Selection**

- เลือกอันดับสูงสุดเฉพาะเหรียญที่ผ่านเกณฑ์คุณภาพและ Risk Manager
- ไม่ต้องให้ทุกอินดิเคเตอร์ส่งสัญญาณพร้อมกัน แต่ต้องมีกลยุทธ์อย่างน้อยหนึ่งชุดให้สัญญาณซื้อที่สมบูรณ์
- หากมีสถานะว่าง 1 ช่อง เลือกได้อีก 1 เหรียญ
- หากเต็ม 2 สถานะ ห้ามเปิดใหม่
- หากไม่มีเหรียญผ่านเกณฑ์ ระบบรอโดยอัตโนมัติ และแสดงเหตุผลว่าไม่ซื้อเพราะอะไร
- ห้ามบังคับซื้อเพียงเพื่อให้บอทแสดงว่ากำลังทำงาน

## 4. Trading Strategy Engine

รองรับกลยุทธ์เริ่มต้น 3 รูปแบบ

1. **Trend Following:** ซื้อเมื่อแนวโน้มและ Momentum สนับสนุน
2. **Breakout:** ซื้อเมื่อทะลุกรอบราคาพร้อมปริมาณซื้อขายที่เหมาะสม
3. **Mean Reversion:** ใช้เมื่อสภาวะตลาดแกว่งตัวในกรอบและมีเงื่อนไขความเสี่ยงรองรับ

AI ช่วยประเมิน Market Regime แล้วเสนอว่าจะใช้กลยุทธ์ใด แต่การส่งคำสั่งต้องผ่านกฎเชิงตัวเลขที่ตรวจสอบได้

ทุกสัญญาณต้องมี `signal_id`, เหรียญ, กลยุทธ์, เวลาสัญญาณ, ข้อมูลประกอบ, ราคาอ้างอิง, จุดออก และเหตุผล

## 5. Risk Management

**ค่าตั้งต้นบังคับ**

| ตัวแปร | ค่า |
|---|---|
| Initial Capital | 10,000 THB |
| Risk Per Trade | 1% สูงสุด 100 THB ตามทุนอ้างอิง |
| Max Open Positions | 2 |
| Daily Loss Limit | 3% เริ่มต้น 300 THB |
| Leverage | 1x (Spot เท่านั้น) |
| Max Capital Per Position | 4,000 THB |
| Max Total Exposure | 8,000 THB |
| Daily Reset | 00:00 น. เวลา Asia/Bangkok |
| Emergency Stop | เปิดใช้งาน |

เมื่อมูลค่าทุนเริ่มวันต่ำกว่า 10,000 บาท ให้ลดวงเงินเสี่ยงต่อรายการและวงเงินขาดทุนรายวันตามทุนจริง ห้ามเพิ่มเกินเพดานเริ่มต้นโดยอัตโนมัติ

**Position Sizing**

คำนวณวงเงินซื้อจากความเสี่ยงที่ยอมรับ ไม่ใช่หารทุนเป็นสองส่วนเท่ากัน

`Position THB ≤ Risk Budget / (Stop Distance + Round-trip Fees + Slippage Allowance)`

ตัวอย่าง: Stop-Loss 2%, ค่าธรรมเนียมรวม 0.50%, สำรอง Slippage 0.20% จะได้ขนาดสถานะประมาณ 3,700 บาท เพื่อจำกัดความเสี่ยงตามแบบจำลองไว้ใกล้ 100 บาท

**กฎหยุดซื้อรายวัน**

คำนวณ P&L ของวันที่เริ่มต้นจาก Equity เวลา 00:00 น. รวมกำไรขาดทุนที่รับรู้แล้ว กำไรขาดทุนที่ยังไม่ปิด และค่าธรรมเนียม พร้อมปรับผลจากการฝากถอนออกจากการคำนวณ

หาก Daily P&L ต่ำกว่าหรือเท่ากับ -300 บาทตามฐานเริ่มต้น ให้เปลี่ยนสถานะเป็น `DAILY_LOSS_LOCK` ทันที

เมื่อถูกล็อก:
- ไม่ส่งคำสั่งซื้อใหม่
- ยกเลิกคำสั่งซื้อที่ยังค้าง
- ยังคงอนุญาตให้ลดหรือปิดสถานะที่มีอยู่
- ไม่ปลดล็อกเพียงเพราะราคาดีดกลับในวันเดียวกัน
- เปิดซื้อใหม่ได้หลังเปลี่ยนวันก็ต่อเมื่อการตรวจสอบสุขภาพระบบและความเสี่ยงผ่าน

ระบบต้องมี Kill Switch แยกต่างหากสำหรับหยุดการส่งคำสั่งทั้งหมด หรือหยุดเฉพาะการเปิดสถานะใหม่

## 6. Execution Engine

รองรับ Limit Order และ Market Order ตามประเภทที่ Bitkub API อนุญาต

ใช้ Limit Order พร้อมตรวจ Spread และราคาสูงสุดที่ยอมรับเป็นแนวทางเข้าซื้อปกติ ส่วนการขายเพื่อลดความเสี่ยงต้องมีกฎสำรองสำหรับสภาพตลาดผิดปกติ

ทุกคำสั่งมี `client_order_id` ไม่ซ้ำกัน และบันทึกสถานะก่อนส่งออกไปยัง Exchange

ต้องจัดการ:
- Partial Fill
- Order Timeout
- Cancel Pending
- API 429 / Rate Limiting
- API Disconnect
- WebSocket Reconnect
- Duplicate Order Prevention
- การกู้คืนสถานะหลัง Backend Restart

เมื่อไม่ทราบว่าคำสั่งสำเร็จหรือไม่ ห้ามส่งคำสั่งเดิมซ้ำทันที ต้องตรวจสอบจาก Order Info, Open Orders, ประวัติการจับคู่ และยอดคงเหลือก่อน

การออกจากสถานะตาม Stop-Loss ต้องทำงานที่ Backend โดยไม่พึ่งเบราว์เซอร์ พร้อมระบบเฝ้าระวังอิสระ เพราะไม่ควรสมมติว่าคำสั่ง Stop-Loss จะถูกเก็บและทำงานบน Exchange เสมอไป

## 7. Backend Architecture

**แนวทางที่เลือก:** Docker บน VPS หรือ Container Host ที่เปิดทำงานต่อเนื่อง พร้อม Supabase PostgreSQL และ Frontend บน Cloudflare Pages

แยกบริการดังนี้

| Service | บทบาท |
|---|---|
| Market Data Service | รักษาการเชื่อมต่อ Public WebSocket |
| Strategy Worker | วิเคราะห์ราคาและเลือกสัญญาณ |
| AI Agent Service | วิเคราะห์ข่าวและบริบทตลาด |
| Risk Service | บังคับใช้กฎการเงิน |
| Execution Service | เชื่อม Private API และจัดการคำสั่ง |
| Reconciliation Worker | ตรวจเทียบคำสั่งและ Wallet กับ Bitkub |
| Health Monitor | ตรวจ Heartbeat และสั่ง Restart หรือ Safe Mode |
| Dashboard API | ให้ข้อมูลหน้าเว็บผ่านสิทธิ์ผู้ใช้ |

ต้องมีระบบ Single Active Executor เพื่อป้องกัน Backend มากกว่าหนึ่งตัวส่งคำสั่งซ้ำ

หาก Market Data ไม่สด, ยอด Wallet ตรวจสอบไม่ได้, Risk State ไม่พร้อม หรือ Backend ขาดการติดต่อ ให้เข้าสู่ Safe Mode โดยปฏิเสธการเปิดสถานะใหม่ และแจ้งเตือนเจ้าของระบบ

## 8. Database — Supabase

สร้างตารางเฉพาะระบบเทรด ไม่ปะปนกับระบบอื่น

| Table | ข้อมูล |
|---|---|
| `bot_settings` | โหมดทำงานและค่าความเสี่ยง |
| `market_snapshots` | Snapshot ราคาและข้อมูลตลาด |
| `trade_signals` | สัญญาณซื้อขายพร้อมเหตุผล |
| `trading_orders` | คำสั่งซื้อขายและสถานะ |
| `trade_fills` | รายการจับคู่จริงและค่าธรรมเนียม |
| `positions` | สถานะที่ถืออยู่ |
| `equity_snapshots` | มูลค่าทุนและสินทรัพย์ย้อนหลัง |
| `daily_pnl` | รายงานกำไรขาดทุนรายวัน |
| `agent_decisions` | ข้อเสนอของ AI และผลการอนุมัติ |
| `risk_events` | เหตุการณ์ปฏิเสธคำสั่งและการหยุดซื้อ |
| `bot_heartbeats` | สถานะการทำงานของแต่ละ Service |
| `audit_logs` | ประวัติการเปลี่ยนค่าและสิทธิ์ผู้ใช้ |

ต้องใช้ Unique Constraints, Transactions และ Row Level Security ตามความเหมาะสม

API Secret ต้องอยู่ในระบบจัดการ Secret ฝั่ง Backend เท่านั้น ไม่เก็บเป็น Plain Text ในฐานข้อมูล ไม่ส่งมาหน้าเว็บ และไม่อนุญาตสิทธิ์ถอนสินทรัพย์

## 9. Dashboard Requirements

**หน้า Overview**
- ทุนตั้งต้น / Equity ปัจจุบัน
- เงิน THB ที่ใช้ได้และเงินที่ถูกจอง
- กำไรขาดทุนวันนี้ ทั้ง Realized และ Unrealized
- กำไรขาดทุนสุทธิหลังหักค่าธรรมเนียม
- สถานะที่เปิดอยู่สูงสุด 2 รายการ
- การใช้วงเงินความเสี่ยงรายวัน
- สถานะ Backend, API และ WebSocket

**หน้า AI Market Scanner**

แสดงอันดับเหรียญ คะแนนวิเคราะห์ สัญญาณล่าสุด ความสดของราคา และเหตุผลที่ผ่านหรือไม่ผ่านเงื่อนไข

**หน้า Orders & Positions**

แสดงราคาซื้อ จำนวนที่จับคู่ ราคาเป้าหมาย Stop-Loss ราคาปัจจุบัน กำไรขาดทุน และประวัติคำสั่ง

**หน้า Profit Analytics**

รายงานรายวัน รายสัปดาห์ รายเดือน Equity Curve, Win Rate, Profit Factor, Maximum Drawdown และผลหลังหักค่าธรรมเนียม

**หน้า AI Agent Monitor**

แสดง Agent แต่ละหน้าที่ กิจกรรมล่าสุด ผลการตัดสินใจ และเหตุการณ์ผิดพลาด รองรับการเพิ่มออฟฟิศ Animation ในรุ่นต่อไป โดยต้องอิงสถานะงานจริง

**หน้า Settings & Safety**

มีปุ่ม Pause, Resume, Emergency Stop, ตั้งค่า Risk Limit และดูประวัติการเปลี่ยนค่า ส่วนการเปิด Live Trading ต้องมีกระบวนการยืนยันแยกจากปุ่มเปิดบอททั่วไป

## 10. Safety Modes

| Mode | สิ่งที่ทำได้ |
|---|---|
| `READ_ONLY` | อ่านข้อมูลราคาและบัญชีโดยไม่ซื้อขาย |
| `PAPER_ONLY` | วิเคราะห์และจำลองคำสั่งด้วยข้อมูลตลาดจริง |
| `LIVE_LOCKED` | เตรียมระบบ Live แต่ยังส่งคำสั่งจริงไม่ได้ |
| `LIVE_ENABLED` | ส่งคำสั่งจริงได้เมื่อได้รับอนุมัติและผ่านการตรวจ |
| `DAILY_LOSS_LOCK` | ปิดการซื้อใหม่ แต่จัดการสถานะค้างได้ |
| `EMERGENCY_STOP` | หยุดการทำงานตามนโยบายฉุกเฉิน |

ค่าเริ่มต้นต้องเป็น `PAPER_ONLY` และ Backend ต้องปฏิเสธทุกคำสั่งที่พยายามเข้าถึง Place Bid / Place Ask จริง

**การปลดล็อก Live ต้องอาศัยการอนุมัติอย่างชัดเจนจากเจ้าของระบบ และต้องตรวจสิทธิ์จาก Server ไม่ใช่เพียงปุ่มบน Frontend**

## 11. Testing & Acceptance Criteria

ก่อนเปิดเงินจริง ต้องผ่านการตรวจสอบดังนี้

- อ่านราคาและข้อมูล Wallet ได้ถูกต้อง
- ไม่มีการเรียก Endpoint ซื้อขายจริงระหว่างทดสอบ
- ทดสอบ Backtest แบบป้องกัน Look-ahead Bias พร้อมค่าธรรมเนียมและ Slippage
- Paper Trading ด้วยข้อมูลตลาดเรียลไทม์อย่างน้อย 7 วัน
- ไม่เปิดเกิน 2 สถานะ รวมรายการซื้อที่กำลังรอจับคู่
- ไม่เกินวงเงินเสี่ยงที่คำนวณได้ก่อนเข้าซื้อ
- เมื่อขาดทุนถึงขีดจำกัด ต้องหยุดเปิดซื้อใหม่
- ทดสอบ Backend Restart, API 429, เครือข่ายหลุด และคำสั่งจับคู่บางส่วน
- ไม่มี Duplicate Order เมื่อ Retry หรือ Restart
- ตรวจยอดและรายการจับคู่กับข้อมูล Exchange ได้
- กำไรขาดทุนใน Dashboard ตรงกับรายการธุรกรรมที่กระทบยอดแล้ว
- ทุกการตัดสินใจมีหลักฐานและเหตุผลตรวจย้อนหลังได้
- ผ่าน Security Review และตรวจว่าไม่มี Secret รั่วใน Source Code, Database หรือ Browser
- ผ่านการอนุมัติของเจ้าของระบบก่อนเปลี่ยนเป็น Live

## 12. ลำดับการส่งมอบ

**Phase 1 — Code & Infrastructure Audit:** ตรวจระบบ Bitkub เดิม, API, Auth, Supabase, Worker และปัญหาเทรดช้า

**Phase 2 — Market Data & Scanner:** เชื่อมข้อมูลตลาดจริงและสร้างระบบเลือกเหรียญอัตโนมัติ

**Phase 3 — Strategy & Risk:** พัฒนากฎซื้อขาย ขนาดสถานะ และระบบหยุดขาดทุน

**Phase 4 — Paper Execution & Dashboard:** จำลองคำสั่งบน Backend จริงพร้อมรายงานผล

**Phase 5 — Operational Verification:** ทดสอบความเสถียร 24/7, ความถูกต้องของยอดเงิน, Error Recovery และ Security

**Phase 6 — Live Activation:** เชื่อมสิทธิ์ซื้อขายจริงและเปิดใช้งานเฉพาะเมื่อเจ้าของอนุมัติเป็นขั้นตอน โดยเริ่มด้วยวงเงินจำกัด

## เกณฑ์ความสำเร็จ

ระบบต้องสามารถเลือกเหรียญ วิเคราะห์ และควบคุมคำสั่งได้อย่างอัตโนมัติบน Backend โดยไม่ต้องเปิดหน้าเว็บไซต์ แต่ต้องไม่ฝ่าฝืนวงเงินความเสี่ยงหรือส่งคำสั่งเงินจริงก่อนผ่านการตรวจรับ

**กำไรไม่ใช่สิ่งที่รับประกันได้** ความสำเร็จทางเทคนิคต้องวัดจากความถูกต้องของการส่งคำสั่ง ความปลอดภัยของทุน ความเสถียร และความสามารถในการตรวจสอบย้อนหลัง ส่วนความคุ้มค่าทางการลงทุนต้องประเมินจากผลลัพธ์จริงหลังหักต้นทุนทั้งหมด
